17. Observed Issues to Verify (flagged directly from screenshots)

1. Untranslated i18n key shown as a tab label

Finance Overview screen shows a tab literally labeled "nav.balances" instead of a translated label like "Balances" (visible next to "Transactions" and "Employee History"). Verify fix and add a regression test (TC-UI-FIN-002).

2. Department name typo

Admin → Employee Management shows employee "maya" assigned to department "Marekting" — likely a typo for "Marketing". Confirm whether this is seed/test data or an actual persisted department name, and correct at the source since department names are unique keys.

3. "Export Ledger" button appears disabled with zero data

On Finance Overview, "Export Ledger" is greyed out when there are 0 transactions. Confirm this is the intended empty-state behavior rather than a broken control (TC-UI-FIN-005).

4. "Member Since —" shown as a bare dash

Finance Profile's "Member Since" field renders as "—" with no date. Confirm whether account-creation date is expected to be populated for this account, or whether this is a legitimate empty state (TC-UI-FIN-019).

5. Truncated notification text

Several Finance notifications end in "..." (e.g., "A manager has issued a direct grant for 500.00 USD that is waiting for..."). Confirm there is a way to read the full message (tooltip/expand/detail page) — currently no such affordance is visible in the screenshot (TC-UI-FIN-020).

6. Two duplicate approval actions in the API (per ISD note)

ISD explicitly flags that both PettyCash/Approve and Manager/UpdateRequestStatus can approve the same request. This is a design risk for double-submission bugs if both are wired into the UI. Confirm with backend which one the frontend should exclusively use, and regression-test the other is either removed from UI or safely idempotent (TC-MGR-002, TC-MGR-003).

7. Two Finance "Change Password" entry points

Both Finance Settings and Finance Profile screens contain a full Change Password form. Confirm this duplication is intentional UX and not a maintenance/consistency risk (TC-UI-FIN-018).

8. Response envelope casing inconsistency

ISD confirms live samples return both statusCode/data and StatusCode/Data depending on endpoint. This must be handled defensively by the frontend client and should ideally be standardized by backend (TC-X-001).
